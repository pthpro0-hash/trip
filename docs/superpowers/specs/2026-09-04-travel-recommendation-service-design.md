# 여행세상 — 한국 관광 추천 서비스 설계 문서

- 작성일: 2026-09-04
- 상태: 승인 대기 (사용자 검토 전)
- 목적: 실제 창업/사업화를 목표로 하는 국내 여행 추천 웹앱 MVP 설계

## 1. 배경 및 목표

문화체육관광부·한국관광공사가 선정한 "2025~2026 한국관광 100선" 데이터(수도권 22, 강원권 11,
충청권 15, 전라권 18, 경상권 28, 제주권 6 — 라벨 기준 총 100곳)를 기반으로, 사용자가 조건에
맞는 국내 관광지를 찾고 여행을 계획할 수 있는 웹 서비스를 만든다.

> **데이터 건수 참고**: 사용자가 제공한 원본 마크다운 파일을 실제로 파싱해보면 수도권 21곳,
> 경상권 27곳으로, 라벨(22/28)보다 각 1곳씩 적어 실제 데이터는 98곳이다(구현 Task 2에서 확인,
> 섹션 9 참고). 데이터를 조작하지 않고 있는 그대로 98곳으로 MVP를 진행하기로 사용자와 합의했다.

최종적으로는 아래 4가지 추천 방식을 모두 제공하는 것이 목표다.

1. 조건 필터형 추천 (지역/계절/테마)
2. 지도 탐색형 추천
3. 코스(일정) 자동 생성
4. AI 대화형 추천

4가지를 한 번에 구현하면 설계·검증 부담이 커지므로, **MVP부터 단계적으로 확장**하는 전략을
택한다. 수익 모델은 아직 미정이며, 사용자 검증 이후 결정한다(광고, 예약 어필리에이트, 구독 등
후보를 열어둔다).

## 2. 범위

### 포함 (In Scope)
- Phase 1 (MVP): 필터 + 지도 탐색, 관광지 상세 페이지 — 비로그인
- Phase 2: 좌표 기반 코스(일정) 자동 생성
- Phase 3: AI 대화형 추천 (Phase 1~2 로직을 자연어로 감싸는 인터페이스)

### 제외 (Out of Scope, 현재는)
- 회원가입/로그인, 즐겨찾기, 리뷰 (사용자 데이터가 필요해지는 시점에 별도 설계)
- 숙소/맛집 등 외부 데이터 연동, 실시간 정보 (날씨·혼잡도 등)
- 결제/예약 연동 (수익 모델 확정 후 별도 스펙)
- 다국어 지원

## 3. 전체 아키텍처

Next.js(App Router) 기반 웹앱. 데이터가 100건 수준으로 작기 때문에 별도 백엔드 서버 없이
정적 생성(SSG) + 클라이언트 필터링으로 구성한다.

```
여행세상 (Next.js App Router)
├── app/
│   ├── page.tsx              # 메인 (필터 + 지도 탐색)
│   ├── spots/[slug]/         # 관광지 상세
│   ├── course/                # Phase 2: 코스 자동생성
│   └── chat/                  # Phase 3: AI 대화 추천
├── components/
│   ├── map/                  # 카카오맵 래퍼, 마커, 클러스터
│   ├── filter/                # 지역/계절/테마 필터 UI
│   └── spot/                  # 관광지 카드, 상세 패널
├── lib/
│   ├── data/spots.json        # 100선 정제 데이터 (원본 소스)
│   ├── types.ts               # Spot, Region, Season, Theme 등 타입 정의
│   ├── filter.ts               # 필터링 순수 함수
│   ├── course.ts               # Phase 2: 코스 생성 순수 함수
│   └── scripts/parse-md.ts    # 첨부 md → spots.json 변환 스크립트
└── public/
```

**데이터 흐름**: 첨부된 마크다운 파일을 1회성 변환 스크립트(`parse-md.ts`)로 파싱해
`lib/data/spots.json`(구조화 데이터)으로 만든다. 앱 빌드 시 이 JSON을 소스로 정적 페이지를
생성하며, 런타임에는 서버 API 호출 없이 클라이언트에서 필터링/검색을 수행한다.

**지도**: 카카오맵 API 사용 (국내 서비스 특성상 좌표·주소 정확도, 무료 티어, 국내 사용자
친숙도 면에서 우위).

## 4. 데이터 모델

```typescript
interface Spot {
  id: string;              // slug (예: "gyeongbokgung")
  name: string;             // "경복궁"
  region: Region;           // 수도권 | 강원권 | 충청권 | 전라권 | 경상권 | 제주권
  lat: number;
  lng: number;
  summary: string;          // 300자 요약
  highlights: string[];     // 꼭 볼 것 목록
  seasons: Season[];        // 정규화된 계절 태그, 예: ["봄", "가을"]
  seasonNote?: string;      // 원본의 괄호 설명 (예: "벚꽃·한복")
  specialty: string[];      // 지역 특산물
  foods: string[];          // 대표 음식 (2개 이상)
  themes: Theme[];          // 파생 태그: 자연 | 역사 | 액티비티 | 카페거리 | 야경 | 체험 등
}

type Region = "수도권" | "강원권" | "충청권" | "전라권" | "경상권" | "제주권";
type Season = "봄" | "여름" | "가을" | "겨울" | "사계절";
// 초기 후보 태그. 100곳 수동 태깅 작업 중 실제 분포를 보고 최종 확정한다 (섹션 9 참고).
type Theme = "역사유적" | "자연경관" | "테마파크" | "해변" | "야경" | "체험마을" | "산" | "정원" | "섬";
```

**설계 포인트**:
- `seasons`/`themes`는 필터링이 가능하도록 정규화된 배열로 관리한다. 원본의 "봄(벚꽃·한복),
  가을(단풍)" 같은 자유 텍스트는 계절 배열과 `seasonNote`로 분리한다.
- `themes`는 원본 데이터에 없는 파생 필드로, 100곳을 수동으로 태깅해 정확도를 확보한다(자동
  추정 대신 — 100개는 수동 관리 가능한 양).
  > **실제 구현 노트(2026-09-05)**: MVP 구현 단계에서는 이 원칙과 달리 `parse-md.ts`의 정규식
  > 기반 자동 추정으로 태그를 부여했다(빠른 출시를 위한 실용적 타협). 최종 리뷰에서 이로 인한
  > 실제 오탐(예: "부산"의 "산"이 자연경관으로 오인식) 몇 건이 발견되어 정규식을 보정했지만,
  > 스펙이 명시한 "수동 태깅"으로의 전환은 아직 하지 않았다. 섹션 9에 후속 작업으로 기록.
- 이 스키마는 향후 Supabase(Postgres) 테이블로 그대로 이관 가능하도록 설계되었다 —
  사용자 데이터(즐겨찾기 등)가 필요해지는 시점에만 DB로 전환한다.
- Phase 2 코스 생성의 동선 계산은 `lat/lng`만으로 하버사인 공식 기반 거리 계산을 사용하며,
  별도 경로 API는 두지 않는다.

## 5. Phase 1 (MVP): 필터 + 지도 탐색

**목표**: 로그인 없이 100곳을 조건으로 필터링하고 지도에서 탐색 — 사업 검증에 필요한 최소 기능.

**메인 화면**:
- 상단 필터 바: 권역(6개) / 계절 / 테마 다중 선택, AND 조건 조합
- 리스트: 필터링된 관광지 카드 (이름, 요약 일부, 대표 음식 뱃지, 계절 뱃지)
- 지도(카카오맵): 필터링된 장소 마커 표시. 카드 ↔ 마커 상호 하이라이트/스크롤 연동
- 필터 결과 0건 시: 조건을 하나씩 완화한 대안 안내 (예: "계절 조건을 빼면 3곳 있어요")

**관광지 상세 페이지** (`/spots/[slug]`): 요약, 꼭 볼 것, 추천 계절, 특산물, 대표 음식, 지도
위치, 같은 권역 추천 3곳.

**모바일 대응**: 지도/리스트를 탭 전환하는 반응형 레이아웃.

**성능**: 클라이언트 필터링(서버 API 불필요). Next.js SSG로 최초 로딩 시 정적 HTML + JSON
번들을 받고, 이후 상호작용은 전부 클라이언트에서 처리한다.

## 6. Phase 2: 코스 자동생성

**입력**: 여행 기간(1~3일), 시작 권역, 선호 테마.

**로직** (규칙 기반, AI 불필요·비용 없음):
1. 선택 권역 내 장소를 좌표 기반(하버사인 거리)으로 클러스터링
2. 하루 3~4곳 배정 (오전 1~2곳 + 점심 근처 대표 음식 + 오후 1~2곳)
3. 테마 선호 태그가 있으면 가중치를 부여해 우선 배정

**출력**: `1일차: 경복궁 → 점심(설렁탕) → 남산서울타워 → 성수동` 형태의 일정표 + 지도 동선
표시. 로그인 없이도 결과를 URL로 공유/북마크 가능하게 한다(향후 즐겨찾기 기능의 자연스러운
전 단계).

## 7. Phase 3: AI 대화형 추천

**입력**: 자유 텍스트 (예: "가을에 아이랑 갈만한 자연 많은 곳 추천해줘").

**로직**: LLM(Claude API)이 100곳 데이터를 컨텍스트로 사용자 발화를 분석해 조건(권역/계절/
테마)으로 변환하고, Phase 1의 필터 로직·Phase 2의 코스 로직을 그대로 재사용해 결과를 대화체로
설명한다. AI가 별도의 추천 엔진을 새로 만드는 것이 아니라 기존 로직의 "자연어 인터페이스"
역할만 하도록 해 로직 중복을 없앤다.

이 단계부터 LLM 호출 비용이 발생하므로, 수익 모델(구독/사용량 제한 등)을 이 시점에 다시
논의해야 한다 (현재 미정).

## 8. 배포 및 비기능 요구사항

- **배포**: Vercel (Next.js와의 호환성, 무료 티어로 MVP 검증에 충분)
- **SEO**: 관광지 상세 페이지는 SSG로 생성되어 검색엔진 노출에 유리 — 실서비스 유입 채널로
  중요
- **확장 경로**: 사용자 계정/즐겨찾기/리뷰가 필요해지는 시점에 Supabase를 도입하고
  `spots.json`을 테이블로 이관한다 (데이터 모델 설계 시 이미 고려됨)
- **테스트**: `lib/filter.ts`, `lib/course.ts`는 순수 함수로 분리해 유닛 테스트를 용이하게
  구성한다

  해당 Phase 착수 시 별도로 다룬다
- 원본 데이터가 라벨상 100곳이 아니라 실제로는 98곳(수도권 1곳, 경상권 1곳 누락)이라는 점을
  2026-09-05에 확인했다. "100선"은 정부 선정 프로그램의 공식 명칭이므로 유지하되, 서비스 내
  실제 개수 표기(UI 카피, 메타 설명 등)는 98을 기준으로 하거나 "약 100곳" 등으로 표현한다.
  누락된 2곳의 정보를 확보하면 `data/source/`의 원본 파일을 교체하고 파서를 재실행하는 것만으로
  100곳을 채울 수 있는 구조로 이미 설계되어 있다.
